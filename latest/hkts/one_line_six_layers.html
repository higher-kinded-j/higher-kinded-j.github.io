Higher-Kinded-J: Composable Effects and Advanced Optics for Java

One Line, Six Layers

One compiled Effect Path line that edits an order, taken apart into the six layers it uses.

Here is a service method that changes the email address on an order. Its body is one expression, and it comes from a compiled, tested example, so it builds as shown.

  static EitherPath<OrderError, Order> changeEmail(
      OrderRepository orders, UUID id, String newEmail) {
    return orders
        .find(id)
        .toEitherPath(OrderError.notFound(id))
        .map(order -> OrderFocus.customer().email().value().set(newEmail, order))
        .via(orders::save);
  }

orders is an OrderRepository. Its find returns a MaybePath<Order>, and its save returns an EitherPath<OrderError, Order>, refusing an order that has already shipped. OrderFocus is generated by @GenerateFocus on Order, one of the order-service records the Optics chapter introduces. Called for a new order, an unknown id and a shipped order, the method gives three answers:

    Either<OrderError, Order> changed = changeEmail(orders, placed, "ada@example.org").run();
    // Right(Order[id=..., customer=Customer[name=Ada,
    //   email=EmailAddress[value=ada@example.org]], ...])
    Either<OrderError, Order> missing = changeEmail(orders, unknown, "ada@example.org").run();
    // Left(NotFound[orderId=...])
    Either<OrderError, Order> refused = changeEmail(orders, shipped, "ada@example.org").run();
    // Left(AlreadyShipped[orderId=...])

A missing order becomes a NotFound that carries its id. The new address goes in three records deep, and you write none of the copies: the lens rebuilds Order, Customer and EmailAddress. A save that refuses ends the chain with its own reason. Each failure is part of the return type, a value the caller handles, rather than an exception the signature never mentions.

Six layers in one expression

Each step of the line belongs to a different layer of the library, and the last column links the page that teaches it.

No step tests for failure. EitherPath carries a failure as a Left, and each later step passes the Left along without running. The interesting code is in the middle, where the domain logic lives.

Two encodings, one algebra

Higher-Kinded-J offers map, via and their neighbours twice. On a Path, they are methods of a concrete type, as in the line. As type classes, they are methods of interfaces such as Functor<F> and Monad<F>, which work over Kind<F, A>: some container F holding an A, without saying which container. One method written that way serves any container:

What you wantOn a PathAs a type class over Kind<F, A>
Change the value insidepath.map(f)functor.map(f, fa)
Combine two independent valuespath.zipWith(other, f)applicative.map2(fa, fb, f)
Run a step that needs the value and may failpath.via(f)monad.flatMap(f, fa)
Recover from an errorpath.recover(f)monadError.handleError(fa, f)

EitherPath holds an Either and calls it directly: no Kind and no type class instance sit between your call and the Either. The type classes do a different job, one method for any container, as the chapter introduction's totals is. The two agree. Run through Functor and Monad over Kind, the email change gives the same Right or Left as the line for each of the three ids, and the page's test checks it.

GenericPath.of(kind, monad) joins the two encodings: it lifts any Kind, with its Monad, to the Path level. Most application code stays with Paths, and the "Which level am I working at?" tip in the Foundations introduction says when to leave them.

The same skeleton, different verbs

Once the skeleton is in place, a different change is a different middle step. Marking the order paid, or taking a discount off every line, leaves the rest of the line as it was:

  static EitherPath<OrderError, Order> markPaid(OrderRepository orders, UUID id) {
    return orders
        .find(id)
        .toEitherPath(OrderError.notFound(id))
        .map(order -> OrderFocus.status().set(OrderStatus.PAID, order))
        .via(orders::save);
  }

  static EitherPath<OrderError, Order> discountEveryLine(
      OrderRepository orders, UUID id, UnaryOperator<BigDecimal> discount) {
    return orders
        .find(id)
        .toEitherPath(OrderError.notFound(id))
        .map(order -> OrderFocus.lines().price().modifyAll(discount, order))
        .via(orders::save);
  }

The discount uses a traversal, OrderFocus.lines().price(), which reaches every line's price at once, and modifyAll applies the discount to each one. Only the middle step changes, and each is a function from Order to Order, so one method that takes that function could serve all three.

Why OrderError.notFound(id), and not new OrderError.NotFound(id)?

Mid-chain, toEitherPath has no target type to infer from, so it takes its error type from its argument. Given a NotFound, the whole chain's error type becomes NotFound, and the method no longer returns what it declares:

static EitherPath<OrderError, Order> changeEmail(
    OrderRepository orders, UUID id, String newEmail) {
  return orders
      .find(id)
      .toEitherPath(new OrderError.NotFound(id))
      .map(order -> OrderFocus.customer().email().value().set(newEmail, order))
      .via(orders::save);
}

The compiler reports incompatible types: no instance(s) of type variable(s) B exist so that EitherPath<NotFound,B> conforms to EitherPath<OrderError,Order>. A factory typed as the sealed OrderError fixes the error type at the first step, so the chain's type matches what the method declares. Naming the type once works too, as .<OrderError>toEitherPath(new OrderError.NotFound(id)), which the Quickstart uses. Effect compiler errors covers the related case the compiler does not catch: a step whose error type differs from the chain's.
