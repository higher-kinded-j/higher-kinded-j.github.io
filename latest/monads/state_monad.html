State: Updating a Value Step by Step

Each step is handed the state, and returns its result with the state it leaves for the next step.

"State is never simple."

— Rich Hickey, Simple Made Easy

Hickey's charge is against the variable, which braids a value together with time: whoever reads it must know what changed it, and when. A State keeps no variable. Each step is handed one state and gives the next, and the order of the steps is the only time there is.

State at a glance
ModelsA computation that is handed a state, such as a basket, and gives a result with the state it leaves
ReplacesA field that each method changes, or methods that take a value and return a pair of the result and the new value
Effect PathWithStatePath
InstancesFunctor, Applicative, Monad
Choose it whenEach step works from what the steps before it left; otherwise Reader, whose environment no step changes, or compare every type in Choosing a Type

Adding to a basket

A customer's basket changes as they shop, and some steps report something too: whether a line went in, or what the basket comes to. Keep the basket in a field, and every method that changes it shares that field. A method's result then depends on what ran before it, which its signature never says. Pass the basket in and return a pair instead, and every caller must unpack the pair and hand the new basket to the next call. A State<S, A> is that function, from a state S to a result A and the next state, with the handing on done for you.

The code on this page uses these imports, with LineItem from the order records the Optics chapter introduces, and Basket from this chapter's examples:

import java.math.BigDecimal;
import java.util.List;
import java.util.stream.Stream;
import org.higherkindedj.example.book.foundations.Basket;
import org.higherkindedj.example.book.optics.cast.LineItem;
import org.higherkindedj.hkt.effect.Path;
import org.higherkindedj.hkt.effect.WithStatePath;
import org.higherkindedj.hkt.state.State;
import org.higherkindedj.hkt.state.StateTuple;

Basket is a record of the examples' own:

/** The lines a customer has chosen so far. Adding a line gives a new basket. */
public record Basket(List<LineItem> lines) {

  public static final Basket EMPTY = new Basket(List.of());

  public Basket {
    lines = List.copyOf(lines);
  }

  public Basket add(LineItem line) {
    return new Basket(Stream.concat(lines.stream(), Stream.of(line)).toList());
  }

  /** Each line's price times its quantity, summed. */
  public BigDecimal total() {
    return lines.stream()
        .map(line -> line.price().multiply(BigDecimal.valueOf(line.quantity())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
  }
}

Basket.add gives a new basket, and leaves the one it was called on as it was. State makes no copy of the state it hands on. Keep the state an immutable value, as Basket is, since a step that changed it in place would change the caller's object too.

The step add puts a line in the basket if the total stays within LIMIT, which is 100.00, and gives true. Otherwise it gives false, and hands on the basket it was given. A StateTuple holds a step's result and the state it leaves:

  // Adds the line if the basket stays within the limit, and says whether it did
  static State<Basket, Boolean> add(LineItem line) {
    return State.of(
        basket -> {
          Basket bigger = basket.add(line);
          return bigger.total().compareTo(LIMIT) <= 0
              ? new StateTuple<>(true, bigger)
              : new StateTuple<>(false, basket);
        });
  }

LAMP is one lamp at 40.00, SOFA one sofa at 450.00, and BULBS four bulbs at 2.50 each. Add the lamp, then the sofa:

    State<Basket, Boolean> lampThenSofa = add(LAMP).flatMap(_ -> add(SOFA));

    StateTuple<Basket, Boolean> after = lampThenSofa.run(Basket.EMPTY);
    boolean sofaAdded = after.value();
    // false
    BigDecimal total = after.state().total();
    // 40.00

    BigDecimal fromBulbs = lampThenSofa.run(new Basket(List.of(BULBS))).state().total();
    // 50.00

The lamp goes in. The sofa would take the basket to 490.00, so add(SOFA) gives false and leaves the basket holding only the lamp. A State holds no basket of its own, so run the same steps from a basket of bulbs and they start from that one. The lamp joins the bulbs, the sofa is refused again, and the basket comes to 50.00. A test builds the basket it needs and runs the steps from it.

Each step is handed the basket

Nothing runs until run is called. Then flatMap runs add(LAMP) on the basket it was given, and passes the result to _ -> add(SOFA). The step that function returns runs on the basket add(LAMP) left.

The basket goes from each step straight to the next, while each result goes to the function that picks the step after it. Each run starts again from the basket it is given, so running a State twice does its work twice.

A step for each line

A loop can build the chain. Each flatMap is handed the refusals so far, and the step it returns runs on the basket the steps before it left. map adds the line's SKU to the refusals when add gives false:

  // One step for each line: each is handed the basket the step before it left
  static State<Basket, List<String>> addAll(List<LineItem> lines) {
    State<Basket, List<String>> refused = State.pure(List.of());
    for (LineItem line : lines) {
      refused =
          refused.flatMap(
              soFar ->
                  add(line)
                      .map(
                          added ->
                              added
                                  ? soFar
                                  : Stream.concat(soFar.stream(), Stream.of(line.sku())).toList()));
    }
    return refused;
  }


    StateTuple<Basket, List<String>> trip = addAll(List.of(LAMP, SOFA, BULBS)).run(Basket.EMPTY);
    List<String> refused = trip.value();
    // [SOFA]
    BigDecimal tripTotal = trip.state().total();
    // 50.00

A long list makes a long chain. run works through the chain in a loop, not a stack frame for each step, so a chain of 100,000 steps runs on an ordinary thread. That holds for map as well as flatMap, and for the WithStatePath methods the next section shows.

On a WithStatePath

Application code holds a State on a WithStatePath, its Effect Path, and Path.state(state) gives you one. It chains with via, runs one path after another with then, and combines with zipWith, which runs the second path on the state the first one left. Checkout reads the total from the basket the trip leaves:

  // zipWith runs the second path on the basket the first one left
  static WithStatePath<Basket, String> checkout(List<LineItem> lines) {
    return Path.state(addAll(lines))
        .zipWith(
            WithStatePath.inspect(Basket::total),
            (refused, total) ->
                refused.isEmpty() ? "pay " + total : "pay " + total + ", refused " + refused);
  }


    String receipt = checkout(List.of(LAMP, SOFA, BULBS)).evalState(Basket.EMPTY);

receipt is "pay 50.00, refused [SOFA]". evalState gives only the result, execState only the final state, and run the StateTuple with both.

A State always gives a value

A StateTuple always holds a result and a state, so State.pure(null), State.set(null) and a StateTuple built with null throw at the call. A function given to map or inspect that returns null fails the run with f must not return null, and one given to modify fails it with StateTuple.construction state cannot be null. A step with nothing to report gives Unit, as set and modify do. State.of does not check what your function returns, so it must never return null. Values, never null sets out the rule every type follows.

Creating instances

State.of(function) wraps a function from a state to a StateTuple, and State.pure(value) gives a value and leaves the state as it is. State.get() gives the state itself, and State.inspect(f) gives what f reads from it. State.set(state) replaces it, and State.modify(f) changes it, and both give Unit. new StateTuple<>(value, state) takes the result first, but StateTuple.of(state, value) takes the state first. On a Path, Path.state(state), Path.statePure(value), Path.getState(), Path.setState(state) and Path.modifyState(f) start a WithStatePath, and WithStatePath.inspect(f) starts one that reads part of the state.

Working with Kind

Generic code, written once for any container, takes State through its Monad instance, from Instances.monad(state()). The state type is part of the witness, StateKind.Witness<S>, so one instance serves steps over one state type. You widen a State to pass it in, and run the result with STATE.runState, STATE.evalState or STATE.execState. STATE.narrow(kind) gives the State back. These are the extra imports, with those the bank account in the next section uses:

import static org.higherkindedj.hkt.instances.Witnesses.state;
import static org.higherkindedj.hkt.state.StateKindHelper.STATE;

import java.util.Objects;
import org.higherkindedj.hkt.Kind;
import org.higherkindedj.hkt.Monad;
import org.higherkindedj.hkt.Unit;
import org.higherkindedj.hkt.expression.For;
import org.higherkindedj.hkt.instances.Instances;
import org.higherkindedj.hkt.state.StateKind;

    Monad<StateKind.Witness<Basket>> baskets = Instances.monad(state());

    Kind<StateKind.Witness<Basket>, Boolean> lamp = STATE.widen(add(LAMP));
    Kind<StateKind.Witness<Basket>, String> label =
        baskets.map(added -> added ? "added" : "refused", lamp);

    String ran = STATE.evalState(label, Basket.EMPTY);

ran is "added". Widening allocates nothing: every State is already a StateKind, so widen checks for null and returns the same object. STATE.get(), STATE.set(state), STATE.modify(f) and STATE.inspect(f) build a widened step directly. Code that changes a state through any monad, not only State, takes a MonadState, as Changing a basket with MonadState shows. ForState names each step's result, and updates the state through optics.

A month in a bank account

What the Monad instance adds is For, which lists a chain of steps in order rather than nesting them. A bank account shows it. An Account holds its balance and every transaction so far, with the refused ones:

  enum TransactionType {
    OPENING_BALANCE,
    DEPOSIT,
    WITHDRAWAL,
    REJECTED_DEPOSIT,
    REJECTED_WITHDRAWAL
  }

  record Transaction(TransactionType type, BigDecimal amount, String description) {}

  // The balance, and every transaction so far, including those refused
  record Account(BigDecimal balance, List<Transaction> history) {

    Account {
      Objects.requireNonNull(balance, "balance");
      history = List.copyOf(history);
    }

    static Account opened(BigDecimal balance) {
      return new Account(
          balance,
          List.of(new Transaction(TransactionType.OPENING_BALANCE, balance, "Opening balance")));
    }

    Account addTransaction(Transaction transaction) {
      return new Account(balance, Stream.concat(history.stream(), Stream.of(transaction)).toList());
    }

    Account withBalance(BigDecimal newBalance) {
      return new Account(newBalance, history);
    }
  }

A deposit only changes the account, so it is a State.modify, and gives Unit. A withdrawal also says whether it was paid:

  // A deposit changes the account and has nothing to report, so it gives Unit
  static State<Account, Unit> deposit(String description, BigDecimal amount) {
    return State.modify(
        account ->
            amount.signum() <= 0
                ? account.addTransaction(
                    new Transaction(TransactionType.REJECTED_DEPOSIT, amount, description))
                : account
                    .withBalance(account.balance().add(amount))
                    .addTransaction(new Transaction(TransactionType.DEPOSIT, amount, description)));
  }

  // A withdrawal reports whether it was paid, as well as changing the account
  static State<Account, Boolean> withdraw(String description, BigDecimal amount) {
    return State.of(
        account -> {
          if (amount.signum() <= 0 || account.balance().compareTo(amount) < 0) {
            Transaction refused =
                new Transaction(TransactionType.REJECTED_WITHDRAWAL, amount, description);
            return new StateTuple<>(false, account.addTransaction(refused));
          }
          Transaction paid = new Transaction(TransactionType.WITHDRAWAL, amount, description);
          return new StateTuple<>(
              true, account.withBalance(account.balance().subtract(amount)).addTransaction(paid));
        });
  }

For sequences the month over the State monad, so each step is widened with STATE.widen. Each from is given the results so far, and the step it returns runs on the account the step before it left. yield sees every step's result:

  static Kind<StateKind.Witness<Account>, String> month() {
    Monad<StateKind.Witness<Account>> accounts = Instances.monad(state());

    return For.from(accounts, STATE.widen(deposit("Salary", new BigDecimal("20.00"))))
        .from(_ -> STATE.widen(withdraw("Bill payment", new BigDecimal("50.00"))))
        .from(_ -> STATE.widen(withdraw("Groceries", new BigDecimal("70.00"))))
        .from(_ -> STATE.widen(withdraw("Cinema", new BigDecimal("12.00"))))
        .yield(
            (_, bill, groceries, cinema) ->
                "bill paid: %s, groceries paid: %s, cinema paid: %s"
                    .formatted(bill, groceries, cinema));
  }


    StateTuple<Account, String> after =
        STATE.runState(month(), Account.opened(new BigDecimal("100.00")));

    String report = after.value();
    BigDecimal balance = after.state().balance();
    // 0.00
    int transactions = after.state().history().size();
    // 5

report is "bill paid: true, groceries paid: true, cinema paid: false". The salary takes the opening 100.00 to 120.00, and the bill and the groceries take it to 0.00. The cinema is refused and recorded as refused, so the history holds five transactions: the opening balance, the salary, two payments and the refusal. The account records no time, so the same month gives the same history on every run. A transaction that needs a time can read it from a TimeSource passed to the step, which a test fixes.
