Validated: Accumulating Errors

Check every field of a request, and report all the errors in one reply.

"When sorrows come, they come not single spies, / But in battalions."

— William Shakespeare, Hamlet (IV.v)

A form's mistakes come the same way, and a fail-fast check reports them one spy at a time. Validated reports the battalion.

What You'll Learn

  • Report every failed check of a request in one result, instead of one per submit
  • Join independent checks with Validated.accumulate(), and follow them with a check that needs their result
  • Say why generic code gets every error from Validated's map2 but only the first from its flatMap
  • Keep the same checks on a ValidationPath, and know which of its methods stop at the first error
  • Choose between Validated, ValidationPath and Accumulating Assembly

The problem: death by a thousand submits

A customer types a delivery address at checkout and makes three mistakes: no street, no city, and a postcode of XYZ. They press Submit, and the page says "street is required". They fill in the street and submit again, to see "city is required". A third submit finally shows "postcode XYZ is not a UK postcode".

Three round-trips. Three frustrations. Three errors that were all knowable from the very first submission.

The code on this page uses these imports, with Address from the order records the Optics chapter introduces:

import org.higherkindedj.example.book.optics.cast.Address;
import org.higherkindedj.hkt.nonemptylist.NonEmptyList;
import org.higherkindedj.hkt.validated.Validated;

Each check returns a Validated rather than throwing. A Valid holds the checked value, and an Invalid holds the errors in a NonEmptyList, since an invalid result always has at least one:

  // Each check returns a valid value, or its error in a NonEmptyList
  static Validated<NonEmptyList<String>, String> street(String street) {
    return street.isBlank()
        ? Validated.invalidNel("street is required")
        : Validated.validNel(street.strip());
  }

  static Validated<NonEmptyList<String>, String> city(String city) {
    return city.isBlank()
        ? Validated.invalidNel("city is required")
        : Validated.validNel(city.strip());
  }

  static Validated<NonEmptyList<String>, String> postcode(String postcode) {
    return POSTCODE.matcher(postcode).matches()
        ? Validated.validNel(postcode)
        : Validated.invalidNel("postcode " + postcode + " is not a UK postcode");
  }

POSTCODE is a Pattern for the shape of a UK postcode.

Joined with flatMap, each check runs only when the one before it has passed, so the address takes three submits:

  // flatMap runs a check only when the one before it passed
  static Validated<NonEmptyList<String>, Address> oneAtATime(
      String street, String city, String postcode) {
    return street(street)
        .flatMap(s -> city(city).flatMap(c -> postcode(postcode).map(p -> new Address(s, c, p))));
  }


    Validated<NonEmptyList<String>, Address> first = oneAtATime("", "", "XYZ");
    // Invalid(NonEmptyList[street is required])
    Validated<NonEmptyList<String>, Address> second = oneAtATime("1 High Street", "", "XYZ");
    // Invalid(NonEmptyList[city is required])
    Validated<NonEmptyList<String>, Address> third = oneAtATime("1 High Street", "Leeds", "XYZ");
    // Invalid(NonEmptyList[postcode XYZ is not a UK postcode])

Every error in one reply

The three checks do not need one another's results, so none has to wait for another. Passed to Validated.accumulate() as arguments, every check runs, where flatMap put the later checks inside functions it might never call. accumulate() builds the address only when every check passed, and otherwise keeps every error, in the order of the checks:

  static Validated<NonEmptyList<String>, Address> address(
      String street, String city, String postcode) {
    return Validated.accumulate()
        .and(street(street))
        .and(city(city))
        .and(postcode(postcode))
        .apply(Address::new);
  }


    Validated<NonEmptyList<String>, Address> everyError = address("", "", "XYZ");
    // Invalid(NonEmptyList[street is required, city is required,
    //   postcode XYZ is not a UK postcode])
    Validated<NonEmptyList<String>, Address> valid = address("1 High Street", "Leeds", "LS1 4AP");
    // Valid(Address[street=1 High Street, city=Leeds, postcode=LS1 4AP])

The diagram shows the same three checks joined two ways. With flatMap, the first failure ends the run; with accumulate(), every check runs and every error is kept. Bean Validation also reports every violation, but of an object that already exists. A Validated builds the address only when every check passes, and its list of errors can never be empty. For a record with many fields, or errors that name the field they belong to, Accumulating Assembly builds the record with Validated.fields().

When one check needs another

Some checks need the value the others built. Whether the courier delivers to an address can only be asked of a whole address, so that check follows accumulate() with flatMap:

  // This check needs a whole address, so it can only follow the others
  static Validated<NonEmptyList<String>, Address> deliverable(Address address) {
    String area = address.postcode().substring(0, address.postcode().indexOf(' '));
    return COURIER_AREAS.contains(area)
        ? Validated.validNel(address)
        : Validated.invalidNel("the courier does not deliver to " + area);
  }

  static Validated<NonEmptyList<String>, Address> deliveryAddress(
      String street, String city, String postcode) {
    return address(street, city, postcode).flatMap(ValidatedBook::deliverable);
  }

COURIER_AREAS holds the postcode areas the courier serves, such as LS1.

    Validated<NonEmptyList<String>, Address> faraway =
        deliveryAddress("1 High Street", "York", "YO1 7HH");
    // Invalid(NonEmptyList[the courier does not deliver to YO1])
    Validated<NonEmptyList<String>, Address> blank = deliveryAddress("", "", "YO1 7HH");
    // Invalid(NonEmptyList[street is required, city is required])

An address with blank fields never reaches the courier check, so the reply holds only the fields' errors. Independent checks accumulate, and a check that needs their result follows them. Applicative, Selective or Monad? makes the same choice for any container.

On a ValidationPath

Application code can hold the same checks on a ValidationPath. Path.accumulate() keeps every error, as Validated.accumulate() does, and via chains a check that needs the value. These are the extra imports:

import org.higherkindedj.hkt.effect.Path;
import org.higherkindedj.hkt.effect.ValidationPath;

  static ValidationPath<NonEmptyList<String>, Address> deliveryAddressPath(
      String street, String city, String postcode) {
    return Path.accumulate()
        .and(Path.validatedNel(street(street)))
        .and(Path.validatedNel(city(city)))
        .and(Path.validatedNel(postcode(postcode)))
        .apply(Address::new)
        .via(address -> Path.validatedNel(deliverable(address)));
  }


    ValidationPath<NonEmptyList<String>, Address> onThePath = deliveryAddressPath("", "", "XYZ");
    // ValidationPath(Invalid(NonEmptyList[street is required, city is required,
    //   postcode XYZ is not a UK postcode]))

Two of a ValidationPath's methods for joining Paths stop at the first error: zipWith and zipWith3. zipWithAccum, zipWith3Accum, andAlso and andThen keep every error.

Working with Kind

Generic code takes Validated through its instance, from Instances.validated(semigroup). The semigroup is how the instance joins two errors; NonEmptyList.semigroup() appends one list to the other. The instance's map2 to map5 keep every error, and its handleErrorWith can replace the errors with a fallback. These are the extra imports:

import static org.higherkindedj.hkt.validated.ValidatedKindHelper.VALIDATED;

import org.higherkindedj.hkt.Kind;
import org.higherkindedj.hkt.MonadError;
import org.higherkindedj.hkt.instances.Instances;
import org.higherkindedj.hkt.validated.ValidatedKind;

    MonadError<ValidatedKind.Witness<NonEmptyList<String>>, NonEmptyList<String>> checks =
        Instances.validated(NonEmptyList.semigroup());

    Kind<ValidatedKind.Witness<NonEmptyList<String>>, Address> checked =
        checks.map3(
            VALIDATED.widen(street("")),
            VALIDATED.widen(city("")),
            VALIDATED.widen(postcode("LS1 4AP")),
            Address::new);
    Kind<ValidatedKind.Witness<NonEmptyList<String>>, Address> orPickup =
        checks.handleErrorWith(checked, errors -> checks.of(PICKUP_POINT));

    Validated<NonEmptyList<String>, Address> bothErrors = VALIDATED.narrow(checked);
    // Invalid(NonEmptyList[street is required, city is required])
    Validated<NonEmptyList<String>, Address> pickup = VALIDATED.narrow(orPickup);
    // Valid(Address[street=2 Station Road, city=Leeds, postcode=LS1 4DY])

PICKUP_POINT is an Address where an order can be collected instead. The postcode passed, so the reply holds the street's and the city's errors. Validated has instances of other type classes too, such as Traverse and Bifunctor, each an object of its own, and Validated at a glance, at the head of the page, lists them.

The instance's map2 to map5 keep every error, while its flatMap, and the flatMap2 built on it, stop at the first, so generic code gets a different answer from each. Where Validated bends a rule says why the two differ.
