Performance: Where a Stream's Time Goes

Each element costs a call on your own thread, and threads start only where you ask for them.

What You'll Learn

  • Say what each pull costs, and on which thread it runs
  • Know which operations start virtual threads, and when that cost pays for itself
  • Say what chunking saves, and what it does not
  • Choose between a VStream and a Java Stream for a pipeline
  • Run VStreamBenchmark, and read what it measures

What a pull costs

Each element reaches the consumer through a pull: a call that returns a VTask, which gives a step when it runs. A terminal operation run with run() or runSafe() makes every pull on that thread, and starts none. Each operator between the source and the consumer adds a task, a step and a call for every element: nanoseconds, where starting a thread takes microseconds. What a pull gives traces the pulls of a small pipeline.

Building a pipeline runs nothing. map, filter, flatMap and mapTask each wrap the stream they are given, and their functions run only when a terminal operation pulls.

Against a Java Stream

A Java Stream pushes each element through its operations in one loop, and makes no task or step for each element. So for work on data already in memory, such as mapping a list, it is faster than a VStream. A VStream earns its cost when the work for an element waits: a call to another service takes milliseconds, and a pull's nanoseconds vanish beside it.

Starting a virtual thread and waiting for it costs far more than a pull. So a parallel operation pays when each task waits, on I/O or a slow service. For a task that only computes something small, map or mapTask is faster. parEvalMap also waits for the slowest task in each batch; when the order of the results does not matter, parEvalMapUnordered lets each one go as its task completes, as Parallel Operations shows.

What chunking saves

chunk(size) still pulls the source once for every element, and groups what it pulls into batches. So it adds a little to each element, rather than saving anything there. It pays when the batch is what costs: one call to a warehouse or a database for ten orders, in place of ten calls. With parEvalMap after it, that is also one task, and one thread, for each batch rather than each element. A larger batch means fewer calls, more elements held at once, and a longer wait for the first result.

Keeping a pipeline cheap

  • Keep work that only computes in map and filter, on the reading thread, where each adds a little to every element: far less than a task on a thread of its own.
  • Put work that waits in a task: mapTask for one element at a time, and VStreamPar for several at once.
  • Batch a call that takes several elements with chunk, then parEvalMap, as Chunking operations shows.
  • Set the concurrency to what the service accepts, as Parallel Operations explains.

Measuring it yourself

VStreamBenchmark, in hkj-benchmarks, measures these costs with JMH:

./gradlew :hkj-benchmarks:jmh -Pincludes=".*VStreamBenchmark.*"

That run is quick, with the defaults the Options table gives. For figures worth comparing, run more iterations in more forks, and add the GC profiler to see what each operation allocates:

./gradlew :hkj-benchmarks:jmh -Pincludes=".*VStreamBenchmark.*" \
  -Pjmh.warmupIterations=3 -Pjmh.iterations=5 -Pjmh.fork=2 -Pjmh.profilers=gc

The results go to hkj-benchmarks/build/reports/jmh/. Each score is operations per microsecond, so higher is faster, as Reading the Output explains. A filtered run like these overwrites results.json, and the next build's benchmark tests then fail on it, so delete the file before you build.
