Exceptions as values

Much of the JDK reports failure by throwing: Integer.parseInt, new BigDecimal and Files.readString among them. A try/catch block splits the result in two, the value on one path and the exception in the catch block, so the outcome cannot be stored, passed to map or returned as one value. Try<T> runs the call and keeps what happened. A Success holds the value, and a Failure holds the exception the call threw. It is close to an Either whose left side is always an exception, with the try/catch written for you.

The code on this page uses these imports, with LineItem from the order records the Optics chapter introduces:

import java.math.BigDecimal;
import java.nio.file.Files;
import java.nio.file.Paths;
import org.higherkindedj.example.book.optics.cast.LineItem;
import org.higherkindedj.hkt.trymonad.Try;

A wholesaler's feed sends order lines as text, such as LAMP,2,40.00. Reading one calls two methods that throw on text they cannot read, so Try.of runs them:

  // Integer.parseInt and new BigDecimal throw on text they cannot read
  static Try<LineItem> parseLine(String line) {
    return Try.of(
        () -> {
          String[] parts = line.split(",");
          return new LineItem(parts[0], Integer.parseInt(parts[1]), new BigDecimal(parts[2]));
        });
  }


    Try<LineItem> lamp = parseLine("LAMP,2,40.00");
    // Success(LineItem[sku=LAMP, quantity=2, price=40.00])
    Try<LineItem> misspelt = parseLine("LAMP,two,40.00");
    // Failure(java.lang.NumberFormatException: For input string: "two")

Try.of takes a Supplier, and a Supplier cannot throw a checked exception, so javac refuses a call such as Files.readString there, with "unreported exception IOException; must be caught or declared to be thrown":

Try<String> feed = Try.of(() -> Files.readString(Paths.get("feed.csv")));

Try.attempt takes a function that may throw one. MISSING_FEED names a file that does not exist:

  // Files.readString declares IOException, a checked exception
  static Try<String> readFeed(String file) {
    return Try.attempt(() -> Files.readString(Paths.get(file)));
  }


    Try<String> feed = readFeed(MISSING_FEED);
    // Failure(java.nio.file.NoSuchFileException: missing-feed.csv)

Both catch any Exception, checked or not, and so do Try's map, flatMap, recover and recoverWith when their function throws. A caught InterruptedException sets the thread's interrupt flag again. An Error, such as StackOverflowError, propagates out of them, as it passes a catch (Exception e) clause.

Chaining and recovering

On a Success, flatMap passes the value to a step that returns a Try of its own. On a Failure, the step never runs, and the first exception reaches the end:

  static Try<LineItem> requirePositivePrice(LineItem item) {
    return item.price().signum() > 0
        ? Try.success(item)
        : Try.failure(new IllegalArgumentException("price must be positive: " + item.price()));
  }

  static Try<LineItem> checkedLine(String line) {
    return parseLine(line).flatMap(TryBook::requirePositivePrice);
  }


    Try<LineItem> free = checkedLine("LAMP,2,0.00");
    // Failure(java.lang.IllegalArgumentException: price must be positive: 0.00)
    Try<LineItem> unread = checkedLine("LAMP,two,0.00");
    // Failure(java.lang.NumberFormatException: For input string: "two")

map changes a Success's value, and an exception its function throws becomes a Failure too. To leave the failure behind, recoverWith makes another attempt, and recover gives a value in its place:

  // Some feeds put a pound sign before the price, so try again without it
  static Try<BigDecimal> price(String text) {
    return Try.of(() -> new BigDecimal(text))
        .recoverWith(
            error ->
                text.startsWith("£")
                    ? Try.of(() -> new BigDecimal(text.substring(1)))
                    : Try.failure(error));
  }


    Try<BigDecimal> withSign = price("£40.00");
    // Success(40.00)
    Try<BigDecimal> unreadable = price("forty");
    // Failure(java.lang.NumberFormatException: ...)
    Try<String> noFeed = readFeed(MISSING_FEED).recover(error -> "");
    // Success()

A feed that cannot be read counts as empty here, so recover gives an empty String. Neither method runs its function on a Success, and an exception that function throws becomes the new Failure.

Reading a Try

A switch over the two cases reads the result, and the compiler checks that both are handled:

  static String describe(Try<LineItem> result) {
    return switch (result) {
      case Try.Success(LineItem item) -> item.quantity() + " x " + item.sku();
      case Try.Failure(Throwable cause) -> "unreadable line: " + cause.getMessage();
    };
  }

foldFailureFirst(onFailure, onSuccess) does the same with two functions, and takes the failure function first, as Either.fold takes the Left function first. get() returns the value or throws the exception, so it is declared throws Throwable and a caller must catch Throwable; keep it for tests.

Creating instances

Try.success(value) and Try.failure(throwable) build either case directly. A Success always holds a value, so Try.success(null) throws NullPointerException. A function given to Try.of, map or recover that returns null gives a Failure holding a NullPointerException. A flatMap or recoverWith function that returns null in place of a Try throws KindUnwrapException. Values, never null has the rule for every type.

A call to the success-first fold of releases before 0.5.0 does not compile: rename it foldFailureFirst and swap its two functions, or run SwapTryFoldToFoldFailureFirstRecipe, as 0.5.0 deprecation migration shows.

On a TryPath

Application code can hold the same steps on a TryPath. Path.tryPath takes a Try, via chains a step, and toEitherPath turns the exception into an error of your own. From there, via chains on to EitherPath steps with the same error type, here String. These are the extra imports:

import org.higherkindedj.hkt.effect.EitherPath;
import org.higherkindedj.hkt.effect.Path;

  static EitherPath<String, LineItem> lineOrReason(String line) {
    return Path.tryPath(parseLine(line))
        .via(item -> Path.tryPath(requirePositivePrice(item)))
        .toEitherPath(error -> "skipped " + line + ": " + error.getMessage());
  }


    EitherPath<String, LineItem> skipped = lineOrReason("LAMP,2,0.00");
    // EitherPath(Left(skipped LAMP,2,0.00: price must be positive: 0.00))

Working with Kind

Generic code, written once for any container, takes Try through its MonadError instance, whose error type is Throwable, as MonadError shows. The instance works over Kind<TryKind.Witness, A>, so you widen a Try to pass it in, and narrow the result to read it. These are the extra imports:

import static org.higherkindedj.hkt.instances.Witnesses.try_;
import static org.higherkindedj.hkt.trymonad.TryKindHelper.TRY;

import org.higherkindedj.hkt.Kind;
import org.higherkindedj.hkt.MonadError;
import org.higherkindedj.hkt.instances.Instances;
import org.higherkindedj.hkt.trymonad.TryKind;

    MonadError<TryKind.Witness, Throwable> tries = Instances.monadError(try_());

    Kind<TryKind.Witness, LineItem> parsed = TRY.widen(parseLine("LAMP,two,40.00"));
    Kind<TryKind.Witness, LineItem> checked =
        tries.flatMap(item -> TRY.widen(requirePositivePrice(item)), parsed);
    Kind<TryKind.Witness, String> answer =
        tries.handleError(
            tries.map(item -> "read " + item.sku(), checked),
            error -> "skipped: " + error.getClass().getSimpleName());

    Try<String> reply = TRY.narrow(answer);
    // Success(skipped: NumberFormatException)

The line could not be read, so flatMap never ran the price check, and handleError turned the exception into a reply. Widening allocates nothing: Try implements TryKind itself, so widen checks for null and returns the same object.
