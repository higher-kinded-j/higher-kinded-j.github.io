Writer: Keeping a Log Beside the Result

Each step returns its result with what it has to log, and the log's Monoid joins the entries.

An audit log for an order

Paying for an order and shipping it should each leave an entry in the order's audit log. Pass a list to every method that logs, and the log shows nowhere in what a method returns. Return a record of the order and its entries instead, and every caller joins the entries by hand. A Writer<W, A> is that record, a result A together with a log W, and flatMap does the joining.

The code on this page uses these imports, with Order and OrderLenses from the order records the Optics chapter introduces, and AuditEntry from this chapter's examples:

import java.util.List;
import org.higherkindedj.example.book.foundations.AuditEntry;
import org.higherkindedj.example.book.optics.cast.Order;
import org.higherkindedj.example.book.optics.cast.OrderLenses;
import org.higherkindedj.example.book.optics.cast.OrderStatus;
import org.higherkindedj.hkt.Monoid;
import org.higherkindedj.hkt.Monoids;
import org.higherkindedj.hkt.Unit;
import org.higherkindedj.hkt.effect.Path;
import org.higherkindedj.hkt.effect.WriterPath;
import org.higherkindedj.hkt.writer.Writer;

AuditEntry is a record of the examples' own:

/** One thing that happened to an order, kept for the audit log. */
public record AuditEntry(UUID orderId, String event) {

  public AuditEntry {
    Objects.requireNonNull(orderId, "orderId");
    Objects.requireNonNull(event, "event");
  }
}

A Monoid says how logs behave. Its empty() is the log before any step, and its combine joins two logs, like the identity and the accumulator you pass to Stream.reduce. The log here is a list of entries, so AUDIT is the list monoid:

  // The empty log is an empty list, and two logs join into one list
  static final Monoid<List<AuditEntry>> AUDIT = Monoids.list();

pay and ship each return the order with its new status, and the entry they add. emailCustomer here only logs that the email went, so it is a tell: a log entry with Unit as its result:

  // Each step returns the order it changed, with the entry it adds to the log
  static Writer<List<AuditEntry>, Order> pay(Order order) {
    return Writer.of(
        List.of(new AuditEntry(order.id(), "paid")),
        OrderLenses.status().set(OrderStatus.PAID, order));
  }

  static Writer<List<AuditEntry>, Order> ship(Order order) {
    return Writer.of(
        List.of(new AuditEntry(order.id(), "shipped")),
        OrderLenses.status().set(OrderStatus.SHIPPED, order));
  }

  // A step with only something to log is a tell, and gives Unit
  static Writer<List<AuditEntry>, Unit> emailCustomer(Order order) {
    return Writer.tell(List.of(new AuditEntry(order.id(), "customer emailed")));
  }

fulfil joins the three. Writer's own flatMap is given AUDIT, so it knows how to join the logs, and map(_ -> shipped) keeps the shipped order as the result after the email:

  // Writer's own flatMap is given the Monoid that joins the two logs
  static Writer<List<AuditEntry>, Order> fulfil(Order order) {
    return pay(order)
        .flatMap(AUDIT, WriterBook::ship)
        .flatMap(AUDIT, shipped -> emailCustomer(shipped).map(_ -> shipped));
  }

NEW_ORDER is an order for one lamp, not yet paid for. Fulfil it, then read the result with run() and the log with exec():

    Writer<List<AuditEntry>, Order> fulfilled = fulfil(NEW_ORDER);

    Order shipped = fulfilled.run();
    List<String> events = fulfilled.exec().stream().map(AuditEntry::event).toList();
    // [paid, shipped, customer emailed]

shipped is the order with the status SHIPPED, and the log holds three entries in the order the steps ran. No method took the log as a parameter, and a test reads it from the value fulfil returns.

Each step's log joins the log before it

flatMap calls the next step with this step's result, then joins the two logs with the Monoid, the earlier log first.

The order goes from each step to the next, on the dotted lines, while AUDIT joins each step's entries onto the log so far. A Writer is a value, not a description of work to run later: flatMap calls the next step at once. So fulfil has done its work when it returns, and run() only reads the result it holds. A chain built in a loop runs without growing the stack, but a step that calls itself through flatMap recurses as any Java method does. With Monoids.list(), each join copies the log so far, so for a chain of thousands of steps the time grows with the square of the log's length. For a log that long, keep a count or a summary instead, or write each entry out as it happens.

On a WriterPath

Application code holds a Writer on a WriterPath, its Effect Path, and Path.writer(writer, monoid) gives you one. The path holds the Monoid and joins the logs itself, so via is given only the next step. Each step is still put on a path with Path.writer(step, AUDIT), but via joins the logs with the path's own Monoid:

  // A WriterPath holds the Monoid, so via is given only the next step
  static WriterPath<List<AuditEntry>, Order> fulfilOnPath(Order order) {
    return Path.writer(pay(order), AUDIT)
        .via(paid -> Path.writer(ship(paid), AUDIT))
        .via(shipped -> Path.writer(emailCustomer(shipped), AUDIT).map(_ -> shipped));
  }


    WriterPath<List<AuditEntry>, Order> onPath = fulfilOnPath(NEW_ORDER);

    boolean sameAsWriter = onPath.run().equals(fulfil(NEW_ORDER));
    // true

The path gives the same Writer as fulfil. run() gives that Writer, value() the result and written() the log.

A Writer always holds a log and a value

A Writer refuses a null log or result, so Writer.of(null, value), Writer.of(log, null) and Writer.tell(null) throw at the call. Because a Writer does its work when it is built, a function given to map that returns null throws at the map call too, with f must not return null. A function given to mapWritten that returns null throws at the call with Writer.construction log cannot be null. Values, never null sets out the rule every type follows.

Creating instances

Writer.of(log, value) pairs a log with a result, and Writer.value(monoid, value) starts with the monoid's empty log. Writer.tell(log) logs with Unit as its result. On a Path, Path.writer(writer, monoid), Path.writerPure(value, monoid) and Path.tell(log, monoid) start a WriterPath.

Working with Kind

Generic code, written once for any container, takes Writer through its Monad instance, from Instances.writer(monoid). The instance needs the Monoid to join logs, so it takes one, and the log type is part of the witness, WriterKind.Witness<W>. You widen a Writer to pass it in. WRITER.run and WRITER.exec read the result and the log from what comes back, and WRITER.runWriter or WRITER.narrow gives the Writer itself. These are the extra imports:

import static org.higherkindedj.hkt.writer.WriterKindHelper.WRITER;

import org.higherkindedj.hkt.Kind;
import org.higherkindedj.hkt.Monad;
import org.higherkindedj.hkt.instances.Instances;
import org.higherkindedj.hkt.writer.WriterKind;

    Monad<WriterKind.Witness<List<AuditEntry>>> audited = Instances.writer(AUDIT);

    Kind<WriterKind.Witness<List<AuditEntry>>, Order> paid = WRITER.widen(pay(NEW_ORDER));
    Kind<WriterKind.Witness<List<AuditEntry>>, Order> thenShipped =
        audited.flatMap(order -> WRITER.widen(ship(order)), paid);

    int entries = WRITER.exec(thenShipped).size();
    // 2

Widening allocates nothing: every Writer is already a WriterKind, so widen checks for null and returns the same object. Writer is also a Bifunctor, over the log and the result: WriterBifunctor.INSTANCE takes a Writer widened with WRITER.widen2, and Writer at a glance, at the head of the page, lists it. Code that keeps a log through any monad, not only Writer, takes a MonadWriter, as Keeping a log with MonadWriter shows.
