VStream: Lazy Pull-Based Streams

A sequence of elements, each produced by a task only when you ask for it.

"Tape after tape. You don't get the whole story at once. You pull the next one, press play, and hope you're ready for what comes out."

— Dan Powell, Archive 81

Dan Powell's archive is a pull-based stream: no tape plays itself, and nothing moves until he reaches for the next one. A VStream works the same way. Each element comes from a task, which runs only when you pull it, and which may block or fail.

Reading a feed one page at a time

An order service hands out its orders a page at a time, and each page is a call that blocks and may throw an IOException. In plain Java you would write a loop that fetches the next page until one comes back empty. A Java Stream or Iterator built over that loop is lazy too, but it can be read only once. The lambdas you pass to its map and filter cannot throw the feed's IOException. Nothing in it can give a value in place of one failed element, or keep what was read when the feed fails. A VStream<A> describes the sequence instead. It produces nothing until a terminal operation runs it, and you can run it as often as you like. Only a stream read from an iterator or a Java Stream gives its elements once, since a run uses up its source.

The code on this page uses these imports, with Order from the order records the Optics chapter introduces:

import java.io.IOException;
import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;
import org.higherkindedj.example.book.foundations.OrderPage;
import org.higherkindedj.example.book.optics.cast.Order;
import org.higherkindedj.hkt.vstream.VStream;
import org.higherkindedj.hkt.vtask.VTask;

The feed gives an OrderPage, and a courier quotes for delivering an order:

/** One page of an order feed: its number, and the orders on it. A page past the last is empty. */
public record OrderPage(int number, List<Order> orders) {

  public OrderPage {
    orders = List.copyOf(Objects.requireNonNull(orders, "orders"));
  }
}

  // A feed serves orders a page at a time, and a courier quotes for delivering an order.
  // Each call blocks until its service answers, and may throw an IOException.
  interface OrderFeed {
    OrderPage page(int number) throws IOException;
  }

  interface Courier {
    BigDecimal quote(Order order) throws IOException;
  }

VStream.unfold builds a stream from a state, here the next page number, and a function giving a task for each state. The task gives a VStream.Seed, holding the element and the next state, or Optional.empty() to end. flatMap turns each page into its orders:

  // Every order in the feed. A page is fetched only when the stream reaches it, and the empty
  // page past the last ends the stream
  static VStream<Order> orders(OrderFeed feed) {
    VStream<OrderPage> pages =
        VStream.unfold(
            1,
            number ->
                VTask.of(
                    () -> {
                      OrderPage page = feed.page(number);
                      return page.orders().isEmpty()
                          ? Optional.empty()
                          : Optional.of(new VStream.Seed<>(page, number + 1));
                    }));
    return pages.flatMap(page -> VStream.fromList(page.orders()));
  }

  static boolean paid(Order order) {
    return order.status() == OrderStatus.PAID;
  }

  static String customer(Order order) {
    return order.customer().name();
  }

ORDERS holds six orders, four of them paid. PagedFeed serves them two to a page, and records each page it is asked for. Taking the first two paid customers reads two pages, and the third is never fetched:

    PagedFeed feed = new PagedFeed(ORDERS);
    VStream<String> paidCustomers =
        orders(feed).filter(VStreamBook::paid).map(VStreamBook::customer);
    List<Integer> fetchedBeforeRunning = feed.fetched();
    // []
    List<String> firstTwo = paidCustomers.take(2).toList().run();
    // [Ada, Alan]
    List<Integer> fetchedForTwo = feed.fetched();
    // [1, 2]
    List<String> everyPaid = paidCustomers.toList().run();
    // [Ada, Alan, Edsger, Ken]
    List<Integer> fetchedForAll = feed.fetched();
    // [1, 2, 1, 2, 3, 4]

Building paidCustomers fetches nothing. Each run reads the feed again from the first page. fetched() keeps every page asked for, so the last list holds the first run's pages 1 and 2, then the second run's pages 1 to 4, where the empty page 4 ends the stream.

What a pull gives

VStream is a functional interface whose one abstract method, pull(), returns a VTask<Step<A>>. Running that task gives one of these steps:

StepMeans
Emit(value, tail)Here is an element, never null, and tail is the rest of the stream
Skip(tail)No element this time; pull tail next
Fail(error, tail)This element failed with error, and tail is the rest of the stream
Done()The stream has ended

A terminal operation is a loop that pulls, keeps each emitted value, and moves on to the tail. This is the loop that take(2).toList() runs over the feed:

Each arrow ends at the operator that answers it. orders is the unfold and flatMap, and map is left out, since it passes every step straight on. Page 2 is fetched only when pull 5 reaches it, and page 3 never is. When filter rejects Grace, it answers Skip rather than pulling again itself, and flatMap answers Skip as it starts or finishes each page. The loop in toList does the pulling again, so however many orders a filter rejects, the stack does not grow. On the pull after its second element, take answers Done and closes the rest of the stream, so a finaliser upstream, such as a bracket's release, runs.

Creating a stream

FactoryGives
VStream.of(a, b, …), fromList(list)The elements given; fromList reads the list when pulled, without copying it
range(from, to)The integers from from up to, not including, to
iterate(seed, f), generate(supplier), repeat(value)A stream without end, which take or takeWhile limits
unfold(state, f)An element and the next state from a task, until it gives Optional.empty()
fromIterator(iterator), fromStream(stream)The elements of an iterator or a Java Stream, which a run uses up: a later run carries on where the last one stopped
defer(supplier)A stream built afresh each time it runs
empty(), fail(error)A stream that ends at once, or fails at its first pull
bracket(acquire, use, release)A stream that holds a resource while it is read, as Resource-Safe Streaming shows

A stream never holds a null element. VStream.of(null) throws at the call, and a null in a list, iterator or Java Stream fails the stream when that element is pulled, naming the factory, as in VStream.fromList element cannot be null. A function given to map, zipWith or recover that returns null fails it too, closing what the stream opened. A Task Always Gives a Value sets out the rule every lazy type follows.

Shaping a stream

map changes each element with a function, and mapTask with a task, which may block or fail. Here a courier quotes for each paid order:

  // A quote for each paid order, asking the courier only when the stream reaches the order
  static VStream<BigDecimal> shippingQuotes(VStream<Order> orders, Courier courier) {
    return orders.filter(VStreamBook::paid).mapTask(order -> VTask.of(() -> courier.quote(order)));
  }

Every operator is lazy: shippingQuotes asks the courier nothing until the stream runs, and then only for the orders a pull reaches. COURIER quotes 4.99 for every order, so fold adds four quotes:

    BigDecimal shipping =
        shippingQuotes(orders(new PagedFeed(ORDERS)), COURIER)
            .fold(BigDecimal.ZERO, BigDecimal::add)
            .run();
    // 19.96

The other operators are lazy in the same way:

OperatorGives
filter(p)The elements that match p
take(n), takeWhile(p)The first n elements, or those before the first that fails p; the rest is then closed
drop(n), dropWhile(p)The elements after the first n, or from the first that fails p
distinct()Each element once
flatMap(f), via(f)The elements of the stream f gives for each element, one stream after another
concat(other)This stream's elements, then other's, which is not pulled until this one ends
zipWith(other, f)f of each pair, stopping at the shorter stream, so the other may be endless
interleave(other)An element from each stream in turn
chunk(size)Batches of up to size elements, as Parallel Operations shows

An endless stream needs a limit

iterate, generate and repeat never end, so toList, fold and count on one run until an interrupt stops them, as Running a stream says. Limit it first with take or takeWhile. exists and find stop at the first match, so they end on an endless stream too, provided a match comes.

Running a stream

A terminal operation gives a VTask, and nothing is read until that task runs:

OperationGives
toList()Every element
fold(identity, op), foldLeft(initial, f)One value built from every element
headOption(), lastOption(), find(p)The first, the last, or the first matching element, as an Optional
count(), exists(p), forAll(p)How many elements, or whether one or all of them match
forEach(action)Unit, after running action on each element
drain()Unit, after reading every element
runSafe()Every element, or the failure, in a Try

The pulls run on the thread that runs the terminal operation's task. runAsync() starts reading at once, on a virtual thread of its own, and gives a CompletableFuture of every element:

    VStream<Boolean> onAVirtualThread = VStream.of(1).map(_ -> Thread.currentThread().isVirtual());

    List<Boolean> fromRun = onAVirtualThread.toList().run();
    // [false]
    List<Boolean> fromRunAsync = onAVirtualThread.runAsync().join();
    // [true]

A terminal operation stops at an interrupt. Before it starts and between pulls, it checks the thread's interrupt status. Once that is set, it fails with an InterruptedException and closes what it has read, so the finalisers there run. That lets a timeout stop drain() on an endless stream, even one whose pulls never block. The TimeoutException arrives once the stream is closed. A run on a thread that is already interrupted fails before its first pull, and closes nothing, since it has read nothing. An interrupt is a stop, not a failure, so recover, recoverWith, mapError and onError let it through. To give a value when a run is stopped, recover outside what stops it, as in toList().timeout(d).recover(e -> List.of()). A recover inside the timeout gives a value the timeout discards.

VStreamPar runs the tasks for several elements at the same time, each on a virtual thread, as Parallel Operations shows.

When an element fails

PATCHY_COURIER quotes as COURIER does, except for Edsger, whose address it does not serve. A failed task makes its element a Fail step. Without a recover, the stream fails there, and runSafe() holds the exception the task threw. recover gives a value in its place, and the stream carries on with the next order. This is the extra import:

import org.higherkindedj.hkt.trymonad.Try;

    VStream<BigDecimal> patchy = shippingQuotes(orders(new PagedFeed(ORDERS)), PATCHY_COURIER);

    Try<List<BigDecimal>> held = patchy.toList().runSafe();
    // Failure(java.io.IOException: no courier serves Edsger's address)
    List<BigDecimal> withFlatRate = patchy.recover(error -> FLAT_RATE).toList().run();
    // [4.99, 4.99, 9.99, 4.99]

run() throws the failure instead, wrapping a checked one as Running a task describes.

When the source itself fails, there is nothing to carry on with. A feed that goes down at page 2 fails the stream there. recoverWith puts another stream in place of the rest, here an empty one, so the orders read before the outage are kept:

    VStream<String> downAtPageTwo = orders(new PagedFeed(ORDERS, 2)).map(VStreamBook::customer);

    List<String> readBeforeTheOutage =
        downAtPageTwo.recoverWith(error -> VStream.empty()).toList().run();
    // [Ada, Grace]
OperatorWhen the stream fails
recover(f)Gives f's value. After a failed task, in mapTask or a parallel operation, the stream carries on with the next element. After any other failure, such as a map function that throws or a failed source, it ends
recoverWith(f)Reads the stream f gives in place of the rest
mapError(f)Fails with the exception f gives instead
onError(action)Runs action, then fails as before

Each acts on a failure at whichever element it happens, not only the first. An interrupt is not a failure, as Running a stream says. recoverWith, and recover when it ends the stream, close the stream they stop reading, so a finaliser upstream runs.

Operators between mapTask and recover

When recover carries on after a failed mapTask task, the operators between the two apply to the elements after it as well. The failed element keeps its place in the stream. In mapTask(quote).filter(cheap).take(3).recover(f), the filter tests the quotes after it, and take counts it as one of its three.

Working with Kind

Generic code, written once for any container, takes VStream through its instances. Instances.monad(vstream()) gives a VStreamMonad, whose flatMap puts a stream in place of each element. These are the extra imports:

import static org.higherkindedj.hkt.instances.Witnesses.vstream;
import static org.higherkindedj.hkt.vstream.VStreamKindHelper.VSTREAM;

import org.higherkindedj.hkt.Kind;
import org.higherkindedj.hkt.Monad;
import org.higherkindedj.hkt.instances.Instances;
import org.higherkindedj.hkt.vstream.VStreamKind;

    Monad<VStreamKind.Witness> streams = Instances.monad(vstream());

    Kind<VStreamKind.Witness, String> customers = VSTREAM.widen(VStream.of("Ada", "Alan"));
    Kind<VStreamKind.Witness, String> greetings =
        streams.flatMap(name -> streams.of("Dear " + name), customers);
    List<String> letters = VSTREAM.narrow(greetings).toList().run();
    // [Dear Ada, Dear Alan]

Widening allocates nothing: VStream implements VStreamKind itself, so widen hands back the same stream, and narrow checks it is one. HKT and Type Classes covers the other instances, and what ap and orElse mean for a stream.
